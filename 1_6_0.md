# M31A v1.6.0 — Premium Terminal Interaction Audit

## CRITICAL Findings

---

### C1: `BuildSemanticStyles()` Allocated Per-Frame During Streaming

**Problem:** `theme.BuildSemanticStyles()` allocates ~120 `lipgloss.Style` objects each call. It is invoked from rendering paths that run every frame during streaming (5-10 FPS), creating 600-1200 style allocations per second that could be avoided with the existing `StyleCache`.

**Evidence:**
- `repl_view.go:325` — `renderWaveSeparator()` calls `BuildSemanticStyles()` every `ViewContent()` call
- `repl_view.go:349` — `renderSlashSuggestions()` calls it when visible
- `repl_scrollbar.go:32` — `overlayScrollbar()` calls it every frame
- `repl_footer.go:51,193,253` — `RenderStatusBar()` calls it per render
- `toolcard.go:115` — `NewToolCard()` calls it per instance
- `theme/cache.go:107` — `StyleCache.SemanticStyles` exists but is unused by most paths

**User Impact:** GC pressure during streaming causes micro-stutters. Each GC pause (even 1-2ms) disrupts the 100ms render cadence, causing visible flicker during LLM streaming — the most interaction-critical moment.

**Implementation Complexity:** Low. Replace `theme.BuildSemanticStyles(t)` calls with `m.styleCache.SemanticStyles` (or pass cache through render context). Requires threading the cache into ~8 call sites.

**Regression Risk:** Low. Cache is already built on theme change. Style values are identical.

**Priority:** Critical

---

### C2: Emitter Channel Drops Workflow Messages Silently

**Problem:** The workflow→TUI bridge channel (`emitterCh`) has a 128-message buffer with a 500ms send timeout. Under heavy parallel tool execution, messages are dropped silently. The `droppedMsgCount` atomic counter tracks drops but is never surfaced to the user.

**Evidence:**
- `app_channel.go:25-33` — `Emit()` drops on timeout with `slog.Warn`
- `streaming/streaming.go:207-212` — drain reads one message per 100ms tick
- During active workflow with 4+ parallel tools, 128 messages fills in ~16 seconds of burst

**User Impact:** During autonomous execution, task start/complete events, tool progress, and phase transitions can disappear. The user sees incomplete progress on the Execute screen, missing tool cards in the REPL, and no indication that events were lost. This directly undermines the "trustworthy autonomous interface" goal.

**Implementation Complexity:** Medium. Options: (a) increase buffer to 512, (b) batch events, (c) surface drop count in status bar, (d) drain multiple messages per tick under load.

**Regression Risk:** Medium. Changing drain behavior affects Bubble Tea's single-threaded contract. Buffer increase is safe.

**Priority:** Critical

---

### C3: Permission Modal Has No Batch Approval

**Problem:** Each tool call requires individual modal approval. There is no "batch approve" or "approve all for this task" option. During autonomous execution with 10+ sequential tool calls requiring permission, the user must approve each one individually.

**Evidence:**
- `tools/permissions.go:209-242` — three `askPermission*` variants, all single-request
- `components/permission.go:42-148` — modal shows Y/A/N for single tool only
- `app_update.go:1757-1777` — `handlePermissionResponse()` processes one response

**User Impact:** In autonomous mode, each dangerous tool call interrupts the workflow with a full-screen modal. For a plan with 8 bash commands, the user must approve 8 times. This defeats the purpose of autonomous execution and creates frustration.

**Implementation Complexity:** Medium. Add "approve all remaining" option (key `A` already exists but only persists for exact-match rules). Need to add session-scoped approval queue with "approve all pending + future same-tool" semantics.

**Regression Risk:** Medium. Must not weaken security. Batch approval should be scoped to current task/phase and require explicit opt-in.

**Priority:** Critical

## HIGH Findings

---

### H1: Context Usage Displayed in Three Simultaneous Locations

**Problem:** On Full-width terminals (≥80 cols), context window usage appears in the header, footer, AND sidebar simultaneously. The same percentage and bar graphic is rendered three times per frame.

**Evidence:**
- `layout/page.go:117-121` — header right zone: `ctx [████░░░░] 42%`
- `repl_footer.go:131-133,249-284` — footer: `ctx [████░░░░] 42%`
- `sidebar_model.go:850-929` — sidebar: context bar + percentage + burn rate + cost trend

**User Impact:** Triple-display wastes vertical/horizontal space and creates cognitive overhead. The user processes the same information from three sources, each with different granularity (header: minimal, footer: medium, sidebar: detailed). This adds visual noise without adding understanding.

**Implementation Complexity:** Low. Remove context ring from header and footer on Full breakpoint. Keep sidebar as the authoritative source. Header keeps model/provider only.

**Regression Risk:** Low. Users on narrow terminals still get footer context ring (sidebar not visible). Removing from header is safe as sidebar always shows it at Full width.

**Priority:** High

---

### H2: Sidebar Conditional Sections Cause Layout Jumps

**Problem:** The sidebar has 7+ sections that conditionally render based on state. When sections appear/disappear (tokens first reported, phases change, tools complete), the sidebar content shifts vertically, causing visible jumps in the file tree below.

**Evidence:**
- `sidebar_model.go:738-747` — sections rendered dynamically, no height reservation
- `sidebar_model.go:812-847` — git status pills conditionally add lines
- `sidebar_model.go:966-1013` — tool timeline grows/shrinks
- `sidebar_model.go:850-929` — usage section with burn rate/cost appears after first token usage

**User Impact:** During autonomous execution, the sidebar is the primary status indicator. When sections pop in/out, the file tree jumps, making it hard to track files. The user's focus is disrupted, and the sidebar feels unstable.

**Implementation Complexity:** Medium. Reserve fixed heights for optional sections (render empty space when section is inactive). Or use a stable section ordering with minimum heights.

**Regression Risk:** Low. Adding empty-line padding when sections are inactive is additive.

**Priority:** High

---

### H3: No Queue Depth or Pending Tool Visibility

**Problem:** During autonomous execution, the user cannot see how many tool calls are queued behind the current one, or what tools are pending approval.

**Evidence:**
- `execute_model.go:170-232` — shows tasks and live output but no tool queue
- `dispatcher.go:200-312` — pipeline has no queue depth reporting
- `app_handlers_workflow.go:98-135` — tool start/complete events don't include queue info

**User Impact:** During long autonomous runs, the user cannot predict how much work remains. They see the current tool executing but don't know if 2 or 20 tools are queued. This reduces trust in the autonomous process.

**Implementation Complexity:** Medium. Add `QueueDepth` field to workflow events. Display in execute screen footer and sidebar.

**Regression Risk:** Low. Additive display change.

**Priority:** High

---

### H4: Verify Phase Has No Real-Time Streaming

**Problem:** The verify phase runs all checks synchronously, then results appear all at once. For large task lists, the user sees a spinner for an extended period with no incremental progress.

**Evidence:**
- `workflow/verify.go:18-210` — `runVerify()` runs all checks in a loop, then emits `VerifyReportMsg`
- `verify_model.go:173-213` — `View()` only renders after results are received
- No `IntermediateProgressMsg` per-task during verification

**User Impact:** During verification of 10+ tasks, the user sees only "Running acceptance checks..." with no progress indication. For complex projects, verification can take 30+ seconds with zero feedback.

**Implementation Complexity:** Medium. Emit `IntermediateProgressMsg` per-task as verification proceeds. Update verify model incrementally.

**Regression Risk:** Low. Additive event emission.

**Priority:** High

---

### H5: Self-Heal Displays No Failure Detail or Diff

**Problem:** When self-healing fails, the user sees "Self-heal failed" but not WHY. There is no diff preview of what changed during a successful heal.

**Evidence:**
- `app_handlers_workflow.go:150-165` — `handleWorkflowSelfHealComplete()` appends "Self-heal ok/failed" with no error detail
- `verify_model.go:256-261` — healing spinner shows attempt count but no error message
- No diff component exists for heal results

**User Impact:** The user cannot understand why verification failed or what the heal attempt changed. This forces manual investigation, undermining autonomous recovery.

**Implementation Complexity:** Medium. Add error message to `SelfHealCompleteMsg`. Add diff preview component (reuse Rollback diff renderer).

**Regression Risk:** Low. Additive information.

**Priority:** High

---

### H6: 256-Color Terminals Get No Fallback Palette

**Problem:** The theme system detects 16-color and TrueColor profiles but has no fallback for 256-color terminals. Hex colors (`#4A6CF7`) are passed through, producing unpredictable results on 256-color terminals.

**Evidence:**
- `theme/colors.go:19-30` — `DetectColorProfile()` returns `ProfileTrueColor`, `Profile256`, or `Profile16`
- `theme/theme.go:191-199` — `resolve()` only handles `Profile16` specially; `Profile256` falls through to hex palette

**User Impact:** On SSH sessions, tmux with 256-color, or older terminals, colors may appear muddy or incorrect. The brand color `#4A6CF7` may map to an unexpected 256-color entry, making the UI look broken.

**Implementation Complexity:** Low. Add `Profile256` case in `resolve()` with a curated 256-color palette mapped from the hex values.

**Regression Risk:** Low. Only affects 256-color terminals (currently broken).

**Priority:** High

---

### H7: Emitter Channel Backpressure Spawns Goroutines

**Problem:** When `TodoWrite` callback finds the emitter channel full, it spawns a goroutine to retry, which can accumulate under sustained load.

**Evidence:**
- `app.go:452-456` — `select { case ch <- msg: default: go func() { m.emitterCh <- msg }() }`

**User Impact:** Under sustained load, multiple goroutines block on the same channel, creating goroutine buildup. Each goroutine holds a message that may be stale by the time it's processed.

**Implementation Complexity:** Low. Replace with bounded retry (3 attempts) or drop with counter.

**Regression Risk:** Low. Currently spawns unbounded goroutines.

**Priority:** High

## MEDIUM Findings

---

### M1: No Dirty-Flag Mechanism for View Rendering

**Problem:** There is no change-tracking system. Every `View()` call recomputes everything from scratch, even if nothing changed since the last frame. The `minRenderInterval` throttle helps during streaming, but idle frames still do full recomputation.

**Evidence:**
- `app_view.go:23-46` — `View()` always calls `renderFrameWithTheme()`
- No `dirty` or `needsRender` flag exists on `AppState` or sub-models

**User Impact:** When the TUI is idle (no streaming, no tool execution), unnecessary CPU is consumed recomputing views. This wastes battery on laptops and creates heat.

**Implementation Complexity:** Medium. Add dirty tracking to sub-models. `View()` returns cached string when clean.

**Regression Risk:** Medium. Must ensure all state mutations set dirty flag. Missing one creates stale display.

**Priority:** Medium

---

### M2: Full Viewport String Rebuild on Message Mutation

**Problem:** `renderMessages()` rebuilds the entire viewport content from all messages on every full render. Any message mutation (like `UpdateLiveTool`) invalidates the entire cache.

**Evidence:**
- `repl_state.go:385-443` — `renderMessages()` iterates all messages
- `repl_state.go:536-538` — `UpdateLiveTool()` calls `renderMessages()` which invalidates `cachedMessageContent`

**User Impact:** During tool execution with live output updates, each update triggers a full message re-render. With 50+ messages, this creates frame drops.

**Implementation Complexity:** Medium. Implement dirty-range tracking: only re-render messages that changed.

**Regression Risk:** Medium. Cache invalidation bugs would cause stale content.

**Priority:** Medium

---

### M3: No Proactive Context Warning at 70%

**Problem:** The context ring changes color at 70% but there is no explicit notification. The user may not notice the subtle color change until context overflow occurs.

**Evidence:**
- `repl_footer.go:249-284` — `renderContextRing()` changes color at 70%/90%
- `repl_stream.go:211` — only error at 95%+: "Context window exceeded"
- No toast or banner at 70% threshold

**User Impact:** Users are surprised by context overflow. The color change is subtle and easy to miss, especially during focused work. Sudden context overflow can lose recent work context.

**Implementation Complexity:** Low. Add toast notification at 70% threshold with `/compress` suggestion.

**Regression Risk:** Low. Additive notification.

**Priority:** Medium

---

### M4: Duplicate Keyboard Hints in Footer and Sidebar

**Problem:** Keyboard shortcuts appear in both the footer and sidebar simultaneously on Full-width terminals.

**Evidence:**
- `layout/page.go:266-274` — footer hints
- `sidebar_model.go:1174-1209` — sidebar hints
- Both visible on Full breakpoint

**User Impact:** Same information displayed twice wastes space and creates visual noise.

**Implementation Complexity:** Low. Remove sidebar hints when footer is visible (Full breakpoint).

**Regression Risk:** Low. Footer is always visible.

**Priority:** Medium

### M5: Sidebar Version and Session ID Are Noise

**Problem:** The sidebar displays "M31A v0.x.y" and a truncated session UUID on every screen. These have minimal practical value during active work.

**Evidence:**
- `sidebar_model.go:794-809` — version badge
- `sidebar_model.go:1161-1171` — session ID

**User Impact:** Two lines of sidebar space consumed by rarely-useful information. On narrow sidebars, this pushes useful content (file tree) below the fold.

**Implementation Complexity:** Low. Move version to `/about` command. Move session ID to Settings screen.

**Regression Risk:** Low. Information still accessible via commands.

**Priority:** Medium

### M6: No Checkpoint Diff Preview

**Problem:** The user cannot see what changed between checkpoints before restoring. With max 2 checkpoints, a wrong restore is costly.

**Evidence:**
- `pkg/session/checkpoint.go:16-25` — Checkpoint stores metadata but no diff
- `resume_model.go:95-187` — resume restores without preview

**User Impact:** Restoring a checkpoint is a blind action. The user doesn't know what they'll lose. This creates anxiety about using checkpoint restore.

**Implementation Complexity:** Medium. Store git diff stat in checkpoint metadata. Show diff preview in resume screen.

**Regression Risk:** Medium. Checkpoint format change requires migration.

**Priority:** Medium

---

### M7: Ghost Mode Has No Diff Preview Before Write

**Problem:** Ghost output shows 5-line content previews but not a full diff. The user cannot verify exact changes before committing.

**Evidence:**
- `ghostoutput_model.go:96-177` — shows content preview (5 lines, 120 chars)
- No diff rendering component used

**User Impact:** The user sees a snippet of generated content but not how it differs from existing files. For modifications to existing files, this is insufficient for safe review.

**Implementation Complexity:** Medium. Reuse diff renderer from Rollback screen. Compute diff against existing file content.

**Regression Risk:** Low. Additive preview.

**Priority:** Medium

---

### M8: Screen Transitions Capture Stale Previous Frame

**Problem:** During the 150ms transition animation, the previous frame is captured at start time. Any content that changes during the animation is lost visually until completion.

**Evidence:**
- `transition.go:41-67` — `StartTransition()` captures `prevFrame` as string
- `app_view.go:31-41` — uses captured `prevFrame` during animation

**User Impact:** If content changes during transition (e.g., streaming continues), the user sees a stale frame slide out and a fresh frame slide in, creating a jarring "jump" at transition end.

**Implementation Complexity:** Medium. Re-render prev frame each animation tick (expensive) or accept the brief stale snapshot (simpler).

**Regression Risk:** Medium. Re-rendering adds frame cost.

**Priority:** Medium

---

### M9: Overlay Compositing Splits Full Viewport

**Problem:** `compositeOverlays()` splits the entire viewport content by `\n`, iterates all lines, and re-joins. This is O(viewportHeight) string operations per frame when overlays are visible.

**Evidence:**
- `repl_view.go:53-91` — `compositeOverlays()` does full split/iterate/join

**User Impact:** When slash commands, @mentions, or quick-actions are visible, each frame pays O(viewportHeight) cost for string operations. At 100 rows, this is 100 string allocations per frame.

**Implementation Complexity:** Low. Pre-compute overlay insertion points. Use `strings.Builder` with targeted writes.

**Regression Risk:** Low. Same visual output.

**Priority:** Medium

---

### M10: DNS Cache Eviction Uses O(N²) Bubble Sort

**Problem:** DNS cache eviction sorts 1024 entries using bubble sort, creating O(N²) comparisons.

**Evidence:**
- `tools/dns_cache.go:148-153` — nested loop bubble sort on entries

**User Impact:** Minimal direct impact (eviction is rare), but under heavy web fetching with many unique domains, eviction could cause latency spikes.

**Implementation Complexity:** Low. Replace with `sort.Slice()`.

**Regression Risk:** Low. Same sort result, faster algorithm.

**Priority:** Medium

## Top 5 Recommendations for v1.6.0 Autonomy Theme

1. **C1 + C2** (Critical): Fix style allocation per-frame and emitter message drops. These directly impact streaming reliability — the core autonomous execution display.

2. **C3** (Critical): Add batch approval for autonomous execution. Without this, "autonomy" requires constant human interruption.

3. **H1 + H2** (High): Clean up triple context display and sidebar layout jumps. These reduce cognitive load during long autonomous sessions.

4. **H3 + H4 + H5** (High): Add queue depth visibility, verify streaming, and heal failure details. These make autonomous execution transparent and recoverable.

5. **H6** (High): Add 256-color fallback palette. Ensures the UI works correctly on SSH/tmux deployments where autonomy is most needed.
