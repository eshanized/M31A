# M31A v1.6.0 — Optimization ROI Review

---

## Scoring Methodology

Each optimization scored 1-10 on 10 criteria:

| Criterion | Definition |
|-----------|-----------|
| **User Impact** | How much the user notices the improvement (10 = constant visible benefit) |
| **Perf Gain** | Raw performance improvement measured by benchmarks |
| **Mem Gain** | Memory reduction (allocations, heap pressure, GC) |
| **Maintainability** | How easy the code is to understand after (10 = simpler) |
| **Complexity** | Architectural complexity of implementation (10 = trivial) |
| **Risk** | Regression risk (10 = zero risk) |
| **Test Ease** | How easy to verify correctness (10 = single benchmark) |
| **Long-term Value** | Value compounds over time (10 = foundation for many future wins) |
| **Effort** | Engineering hours (10 = < 1 hour, 1 = > 1 week) |

ROI formula:
```
ROI = (User Impact * Long-term Value * Perf Gain) / (Effort * Risk * Complexity)
```

Higher ROI = implement first.

### O1: StyleCache Threading

**What:** Replace `theme.BuildSemanticStyles(t)` with cached `StyleCache.SemanticStyles` at all ~12 call sites.

| Criterion | Score | Reasoning |
|-----------|-------|-----------|
| User Impact | 9 | Eliminates streaming micro-stutters. User sees smoother token delivery. |
| Perf Gain | 10 | 1500-2400 allocs/sec eliminated. Largest single allocation hotspot. |
| Mem Gain | 10 | ~1500 lipgloss.Style objects/sec eliminated from heap. |
| Maintainability | 8 | Code becomes clearer: styles are pre-computed, not recomputed. |
| Complexity | 9 | Thread a field through ~12 call sites. No algorithmic changes. |
| Risk | 9 | Cache is rebuilt on theme change. Styles are identical. |
| Test Ease | 9 | Single benchmark proves it: `BenchmarkAlloc_StyleCache` shows 0 allocs. |
| Long-term Value | 10 | Foundation for all other rendering optimizations. Every render path benefits. |
| Effort | 8 | 2-3 days. Mechanical threading, no design decisions. |

**ROI = (9 * 10 * 10) / (8 * 9 * 9) = 900 / 648 = 1.39**

## Rejected Optimizations

### O4: CodeBlock Double-Style — REJECT

**Why:** Subsumed by O1. When O1 threads StyleCache through the pipeline, `RenderCodeBlock` and `renderCodeLines` both receive cached styles. The redundant call disappears. Implementing O4 separately is wasted effort.

**Measurable gain:** 60 allocs per code block. Meaningful but automatically fixed by O1.

### O5: SSE Line Slice Reuse — REJECT

**Why:** 50-200 small allocs per stream (~10KB total). The GC pressure is negligible compared to the 1500-2400 allocs/sec from BuildSemanticStyles. Not worth any engineering time when O1 exists.

**Measurable gain:** ~10KB per stream. Imperceptible to user.

### O10: Lazy Binary Detection — REJECT

**Why:** Saves ~1024 bytes per tool card. The 0.5ms improvement is imperceptible. No user will ever notice this.

**Measurable gain:** ~1024 bytes per tool card. Imperceptible.

### O15: Compile Chroma Lexers — REJECT

**Why:** Lexer lookup is microseconds. The overhead is in tokenization (O(N) per file), not lexer lookup (O(1) map access). Caching the lexer doesn't help the bottleneck.

**Measurable gain:** Microseconds per code block. Imperceptible.

### O17: Codeintel Scanner Reuse — REJECT

**Why:** Code intel runs once at startup. The ~4KB per file saving is minor compared to the 100-5000 files parsed. More importantly, startup is already fast after O8 (background sweep). This is optimizing a one-time cost.

**Measurable gain:** ~4KB per file during one-time startup. Imperceptible after O8.

### O9: Session Buffer Pool — REJECT

**Why:** Session save is background I/O. The user never sees it. The ~200KB allocation per save is absorbed by the next GC cycle without impact. Not worth engineering time when streaming rendering optimizations exist.

**Measurable gain:** ~200KB per background save. Imperceptible.

### O13: Permission Modal Frame Cache — REJECT

**Why:** Subsumed by O11 if single-pass viewport is done. If O11 is not done, the 8ms improvement is below the perception threshold (16ms for animation). Permission modals are infrequent.

**Measurable gain:** ~8ms per permission modal. Below perception threshold.

### O16: JSON Serialization Pool — REJECT

**Why:** JSON serialization is background. User never sees it. The allocation reduction is minor compared to streaming rendering. Not worth the multi-call-site wrapping effort.

**Measurable gain:** Reduced background allocation. Imperceptible.
