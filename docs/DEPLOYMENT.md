# M31A Deployment & Release Channels

This document is the canonical deployment specification. `docs/RELEASE.md`
remains the step-by-step release procedure; this file defines the channel
model, artifact lifecycle, state isolation, and update/rollback behavior.

Product scope: M31A is NVIDIA-only (`nvidia_nim` is the sole
production-supported provider). Deployment never reintroduces other
providers; development and production artifacts both use the same NVIDIA
provider, policy, sandbox, and tool systems.

---

## 1. Core distinction: build profile ≠ deployment channel

Cargo profiles (`[profile.dev]` / `[profile.release]`) are compiler settings.
The deployment channel is domain identity:

```text
DeploymentChannel::Development | DeploymentChannel::Production
```

Valid combinations include development+debug, development+release, and
production+release. Production distribution normally uses optimized release
builds, but the channel remains an explicit concept.

## 2. Channel identity (compile-time)

- `cargo build --release` → **production** (`m31a`, default, no feature).
- `cargo build --release --features development` → **development** (`m31a-dev`).
- `development` + `production` features together are a compile error.
- No runtime switch exists: `M31A_ENV=development` (or any env var) can never
  turn a production binary into a development deployment. The channel is part
  of the artifact identity, reported by `m31a --version` /
  `m31a version --verbose` and `m31a doctor`.

## 3. Lifecycle

```text
development branch/commit
      ↓
development CI (.github/workflows/development.yml)
      ↓
development artifact (m31a-dev, nightly/branch builds, 7-day retention)
      ↓
release candidate (src/release/* state machine + evidence)
      ↓
production verification (gates: version, clean source, tests, identity)
      ↓
production promotion (explicit approval; dirty/blocked → denied)
      ↓
immutable production release (m31a, tagged, checksummed, manifest)
      ↓
stable update channel
```

Development builds never self-promote: a dev artifact becomes production only
through a `ReleaseCandidate` reaching `Candidate` with full evidence plus a
non-empty approval note (`deployment::evaluate_promotion`).

## 4. Version authority

`Cargo.toml` `[package] version` → `CARGO_PKG_VERSION` →
`src/release/version.rs` is the ONLY semantic version authority.

- Production: `m31a 0.1.2`
- Development: `m31a-dev 0.1.2-dev+<build12>`

The `-dev+<build>` suffix is display metadata; the canonical semver is
identical in both channels. Build facts (commit, branch, timestamp, target,
dirty, build ID) are additional provenance from `build.rs`, never a second
version source.

`build_id` = `sha256(version|channel|commit|target)[..16]`: deterministic per
immutable inputs, distinct across commit/target/channel. Runtime instance
UUIDs are separate concepts.

## 5. State isolation

One core runtime, isolated global state:

| Scope | Production | Development |
|:---|:---|:---|
| Binary | `m31a` | `m31a-dev` |
| Global config/data/cache/state | `m31a` app dirs | `m31a-dev` app dirs |
| Socket / PID | `m31a.sock` / `m31a.pid` | `m31a-dev.sock` / `m31a-dev.pid` |
| Update feed | `stable` | `development` |

Project-local `.m31a/` is ONE shared workspace directory:

- Shared: initialization, repository knowledge, workspace config.
- Isolated: runtime/session state under `.m31a/state/<channel>/`,
  project DB (`m31a.db` vs `m31a-dev.db`), sockets, logs.
- Credentials are never auto-copied: `.m31a/credentials.json` (production)
  vs `.m31a/credentials-dev.json` (development).

Production paths are backward compatible: existing `~/.config/m31a/`,
`~/.local/share/m31a/`, and `project/.m31a/m31a.db` keep working unchanged.
Development paths are new and additive.

## 6. Feature gating

Development-only affordances (verbose diagnostics, experimental UI, developer
commands, dev telemetry detail) are gated centrally in
`deployment::FeatureGate`. Gating affects visibility only — policy, sandbox,
capability, approval, containment, and secret controls are identical in both
channels. A development build is never a security bypass.

## 7. Artifacts & manifests

Each artifact records `artifact_id, version, channel, target, format, sha256,
size, build_id, git_commit`. Identity lives in metadata, not filenames.

The deployment manifest (`dist/deployment-manifest.json`, schema v1) is
generated by the release pipeline with `{schema_version, version, channel,
artifacts[]}`. Validation rejects empty/invalid versions, unknown channels,
missing artifacts/checksums, duplicate targets, invalid targets, inconsistent
build IDs, and missing commit metadata. One schema serves both channels.

Signing: the repository defines no signing infrastructure
(`SIGNING_MECHANISM: none`). Integrity rests on SHA-256 verification of every
download before execution; checksums are authenticity-of-bytes, not identity
signatures. The manifest schema reserves `signature`/`signing_identity`
seams for a future mechanism.

## 8. Updates & rollback

```
discover → download → verify checksum → stage → verify executable →
atomically replace → verify runtime (else keep previous binary)
```

- `m31a update --manifest <deployment-manifest.json>` checks (`--check`) or
  applies an update from explicit manifest metadata (offline-first; no model
  involvement, no render-thread network).
- Production consumes only `channel = production` manifests; development only
  `channel = development` — cross-channel consumption is rejected on the
  normal path.
- `m31a rollback` restores the preserved `<binary>.prev` backup.
- Success is reported only after the installed executable verifies.

## 9. Install

```bash
# Production
cargo build --release
./scripts/install-local.sh --channel production   # installs `m31a`

# Development (side-by-side safe)
cargo build --release --features development
./scripts/install-local.sh --channel development  # installs `m31a-dev`
```

User-local install, no root required. Installation replaces only the binary
(preserving `<binary>.prev`); user config/data/state/databases are never
wiped or implicitly migrated.

## 10. Commands

- `m31a --version` / `m31a-dev --version` — one-line channel-aware identity.
- `m31a version --verbose` — full build identity.
- `m31a deployment [--verbose]` — channel, version, target, build, paths.
- `m31a update --manifest <file> [--check]` — channel-safe updates.
- `m31a rollback` — restore previous known-good binary.
- `m31a doctor` — includes a `deployment` probe (channel/version/target/
  build/config source, never secrets).
- `m31a config sources` — reports channel + config source first.
- The cockpit header shows `vX.Y.Z PRODUCTION` or
  `vX.Y.Z DEVELOPMENT · build <short>` unobtrusively.

## 11. CI

- Development (`.github/workflows/development.yml`): pushes to non-master
  branches, PRs, nightly schedule, manual dispatch. fmt/check/clippy/tests/
  security + `m31a-dev` matrix builds uploaded as workflow artifacts
  (7-day retention). Never publishes releases.
- Production (`.github/workflows/release.yml`): published releases (or
  approved manual dispatch) only. Gates (clean source, version==tag,
  fmt/check/clippy/tests) run first; per-target builds verify `m31a X.Y.Z`
  identity, package archives, checksums, and per-target deployment manifests
  before `gh release upload`.
