<objective>
Fix four channel-ownership findings in the streaming pipeline:

- **C-3 (CRITICAL)** — `StartStreamCmd` is invoked twice on the same
  channel pair; the deferred `close(streamCh)` panics with "close of
  closed channel". Channels are currently allocated by the REPL and
  passed into the goroutine, so two owners, one channel.
- **H-9 (HIGH)** — `safeClose` in `app.go` is a non-atomic
  check-then-close; another goroutine can call `close(ch)` between the
  `<-ch` probe and the `close(ch)`, causing a panic. The function is
  supposed to prevent exactly this race.
- **H-14 (HIGH)** — `streamContent` and `streamSegments` on the
  REPL model are mutated by the streaming goroutine and read by the
  BT update loop with no synchronization. The `strings.Builder` and
  the `[]MessageSegment` slice are shared mutable state.
- **M-21 (MEDIUM)** — The `defer close(streamDone)` and
  `defer close(streamCh)` in `streaming.go` are LIFO-ordered, so
  `streamCh` is closed first. The continuation closure in
  `repl_stream.go` selects on `<-streamDone` first; with `streamDone`
  still open, the function deadlocks.

**Architectural rule (per CONTEXT.md):** channels are owned by the
goroutine that writes to them. `StartStreamCmd` becomes a black box
that allocates its own channels and disposes them. The REPL only sees
`StreamChunkMsg` / `StreamDoneMsg` / `StreamErrorMsg` on the BT update
loop.

**Output:** Refactored `internal/tui/streaming.go` and
`internal/tui/repl_stream.go` with single-owner channels; new
`safeCloseOnce` helper in `internal/tui/app.go`; new tests in
`internal/tui/streaming_test.go` covering double-invocation and
race-free close.
</objective>

    Refactor `StartStreamCmd` in `internal/tui/streaming.go` so that
    channel ownership is encapsulated:

    1. Change the signature so the caller (REPL) no longer passes in
       `streamCh` or `streamDone`. The new signature accepts only the
       inputs needed to start a stream: a `ChatRequest` (or its
       equivalent — read the file to determine) and a provider. The
       function returns a `tea.Cmd` that, when invoked by Bubble Tea,
       performs the entire stream lifecycle internally and emits
       `StreamChunkMsg` / `StreamDoneMsg` / `StreamErrorMsg` on the
       BT update loop.

    2. Inside the cmd body (a `tea.Cmd` is `func() tea.Msg`):
       - Allocate `streamCh := make(chan tea.Msg, 64)`,
         `streamDone := make(chan struct{})`, and
         `cancel := make(chan struct{})` as LOCAL variables — they
         are not returned to the caller.
       - Spawn a goroutine that calls `provider.ChatCompletionStream`,
         reads from the returned `*StreamIterator`, and forwards
         each chunk to `streamCh`. On iterator error or `done`,
         close `streamDone` first, then close `streamCh`.
       - The cmd itself returns a single `tea.Msg`:
         - After provider stream starts, return a `StreamChunkMsg`
           (or a new `StreamStartMsg` if one exists already; the
           plan is additive — do not introduce a new message type
           if one already serves the purpose). Read
           `internal/tui/types.go` to confirm.

    3. Fix the LIFO defer-order bug (M-21): reverse the defer order
       so `streamDone` is closed FIRST, then `streamCh`. After
       reversal, the continuation that selects on `<-streamDone` first
       will unblock, then the `<-streamCh` branch drains the buffer
       cleanly. Alternative: keep streamCh as the only channel and
       drop streamDone — the iterator's `Close` provides the same
       signal. Pick whichever requires fewer changes to
       `repl_stream.go`; document the choice in a `// Fix M-21:`
       comment.

    4. Add a `// Fix C-3:` comment block at the top of the function
       explaining the new ownership model: "channels are owned by the
       goroutine that writes to them; the REPL does not hold
       references".

    5. Remove any code in the cmd that reads from the channels after
       the goroutine completes; the BT update loop is responsible
       for the next chunk via the `tea.Msg` it returns.
  </action>

| Boundary | Description |
|----------|-------------|
| Streaming goroutine → BT update loop | Channels are owned by the goroutine; the BT loop only sees `tea.Msg` values. The boundary is the type system — `StreamChunkMsg` is a value type. |
