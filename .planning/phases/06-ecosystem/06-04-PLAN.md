    1. **docs/extensions/api-reference.md** — Complete reference for pkg/extensions public API:
       - Interface definitions: ExternalTool, ExternalProvider, PhaseHookHandler (with all methods)
       - Config structs: ExternalToolConfig, ExternalProviderConfig, PhaseHookConfig, ExtensionsConfig
       - Protocol: JSON-RPC 2.0 method constants, request/response types, handshake flow
       - SubprocessManager: Start(), Call(), Stop() signatures
       - ExtensionRegistry: NewExtensionRegistryFromConfig(), Start(), Stop(), GetTool/GetProvider/GetHooks()
       - Adapter types: ExternalToolAdapter, ExternalProviderAdapter, PhaseHookAdapter constructors
       - Error codes and handling
       - Version compatibility policy (protocol_version in handshake)

    2. **docs/extensions/authoring-guide.md** — Step-by-step guide to build extensions:
       - Prerequisites: Go 1.25+, JSON-RPC 2.0 understanding
       - Extension structure: single executable, stdio communication
       - Building a tool extension: implement 5 methods (name, description, risk_level, schema, execute)
       - Building a provider extension: implement 6 methods (name, fetch_models, chat_completion_stream, estimate_cost, health_check)
       - Building a hook extension: implement PrePhase/PostPhase
       - JSON-RPC implementation patterns (request/response, notifications for streaming)
       - Configuring in m31a.json / config.toml
       - Testing locally: `m31a config show --extensions`, run extension manually
       - Distribution: GitHub Releases, Homebrew formula, Scoop manifest
       - Best practices: timeouts, error handling, logging to stderr, graceful shutdown

    3. **docs/extensions/tutorial.md** — Interactive walkthrough:
       - Step 1: Create a simple "echo" tool extension (5 min)
       - Step 2: Register in config, test with M31A
       - Step 3: Add parameters and schema
       - Step 4: Build a provider extension stub (Ollama)
       - Step 5: Build a hook extension (pre-execute linter)
       - Step 6: Package and distribute
       - Each step has expected output and verification commands

    4. **docs/extensions/testing-guide.md** — Testing patterns:
       - Unit testing: mock SubprocessManager, test adapter logic
       - Integration testing: spawn real extension subprocess, test JSON-RPC
       - Test helpers: test extension binary for CI
       - Contract testing: verify extension implements all required methods
       - CI integration: build extension in CI, test against M31A

    5. **docs/extensions/migration-guide.md** — Converting internal to external:
       - Why migrate: language freedom, independent deployment, isolation
       - Tool migration: extract Execute() logic, wrap in JSON-RPC handler
       - Provider migration: extract ChatCompletionStream, wrap in notifications
       - Hook migration: identify phase transition points, extract logic
       - Config changes: move from code registration to config declaration
       - Testing parity: ensure external behaves identically to internal
       - Rollback strategy: keep internal version during transition

    6. **docs/extensions/faq.md** — Common questions:
       - Q: Why subprocess not WASM/Go plugins? A: CGO_ENABLED=0, cross-platform, language-agnostic
       - Q: How to handle streaming? A: JSON-RPC notifications
       - Q: Can extensions access M31A internals? A: Only via exposed APIs (ToolInput, PhaseHookPayload)
       - Q: How to debug? A: Run extension manually with JSON-RPC on stdin/stdout
       - Q: Protocol versioning? A: Handshake returns protocol_version, major = breaking
       - Q: Performance overhead? A: ~5-10ms per call (subprocess + JSON-RPC)
       - Q: Can extensions call other extensions? A: No direct access; use M31A as mediator

    Follow project conventions: no emojis, structured markdown, code blocks with language tags.
