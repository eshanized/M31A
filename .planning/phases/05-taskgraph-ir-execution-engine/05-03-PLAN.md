    Implement the main Execute() method on Runner that drives wave-based execution per CONTEXT.md D-13, D-14, D-15 and RESEARCH.md Architecture Patterns.

    1. Add LockManager to Runner:
       - locks map[string]chan struct{} (semaphore per lock name, capacity 1)
       - acquireLocks(lockNames []string) — sort lockNames alphabetically (deadlock prevention per Pitfall 5), acquire each in order
       - releaseLocks(lockNames []string) — release in reverse order
       - Initialize locks map in New()

    2. Add CheckpointGate to Runner (or use checkpoint.go CheckpointGate):
       - gate *CheckpointGate (from checkpoint.go)
       - Initialize in New() with EventStore and ApproveCh

    3. Execute(ctx context.Context, ir *types.TaskGraphIR, executeFunc ExecuteFunc) error:
       - Store ir reference, initialize all task states to PLANNED (if not already set)
       - Emit EventTaskGraphCreated with TaskGraphCreatedPayload{TaskGraphIR: *ir}
       - For each waveIndex, wave := range ir.Waves:
         * Before wave: check if any task in wave has ONE_WAY_DOOR checkpoint (scan ir.Checkpoints for checkpoint.TaskIDs intersecting wave)
         * If checkpoint exists: call gate.RequestApproval(ctx, checkpoint, r.RunID) — blocks until approval
         * If denied/cancelled: transition checkpoint tasks to FAILED, return error
         * Call r.ExecuteGroup(ctx, wave.TaskIDs, executeFunc) — existing method, updated to use ExecutionState
         * After ExecuteGroup: check all tasks in wave reached terminal state (IsTerminal())
         * For any task FAILED: find dependents in ir.Dependencies, transition them to SKIPPED with reason "dependency failed"
         * If context cancelled: return ctx.Err()
       - After all waves: return nil

    4. Update ExecuteGroup (from Plan 05-01 tracer patterns):
       - Use r.transitionTask for all state changes (emits events)
       - Check task.LockNames before execution: r.acquireLocks(task.LockNames); defer r.releaseLocks(task.LockNames)
       - Per-task timeout: context.WithTimeout(ctx, r.TaskTimeout)
       - Retry loop uses r.MaxRetries, calls r.handleFailure on failure (from Plan 05-02)
       - On success: transition to VERIFYING (not COMPLETED yet — verification is separate phase)
       - On failure after retries exhausted: task.RecoveryAction determines next step (RETRY/REPAIR/REPLAN/ESCALATE)

    5. Config integration:
       - Read max_parallel_tasks from config.Execution.MaxParallelTasks (default 4)
       - Read task_timeout from config.Execution.TaskTimeout (default 30m)
       - Read wave_timeout from config.Execution.WaveTimeout (default 0 = no limit)
       - Add WithConfig(cfg *config.Config) RunnerOption

    6. checkpoint.go CheckpointGate:
       - Implement per RESEARCH.md Pattern 3 and PATTERNS.md
       - RequestApproval emits CheckpointRequested event, blocks on ApproveCh
       - Approval includes CheckpointID for correlation (fix Pitfall 3)
       - On approval: emit CheckpointApproved event
       - On denial/timeout: emit CheckpointDenied event

    Note: ExecuteFunc signature: func(ctx context.Context, task types.TaskIR) types.TaskResult. The actual task execution logic (calling agents, tools) comes in Phase 6/7. For now, ExecuteFunc is a callback — tests provide a mock.
