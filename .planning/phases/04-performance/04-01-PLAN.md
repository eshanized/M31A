# 04-01: Startup Lazy Loading

## Goal

Defer provider registration, keychain initialization, and config validation until first LLM call, reducing startup latency from ~300-700ms to under 500ms.

## Locked Decisions

- D-01: Target under 500ms from binary invocation to first interactive prompt
- D-02: Pure lazy loading -- defer providers, config validation, keychain until first LLM call
- D-03: Config errors surface at first use, not at startup
- D-04: No background warm-up goroutines

## Tasks

### Task 1: Create lazy provider registry wrapper

<read_first>
- internal/integrations/provider/registry.go
- cmd/m31a/main.go
</read_first>

<action>
Create a `LazyRegistry` type in `internal/integrations/provider/registry.go` that wraps `*Registry` and defers provider registration until first access via `ActiveProvider()` or `Active()`.

The `LazyRegistry` struct holds:
- `once sync.Once` -- triggers one-time initialization
- `initFn func()` -- closure that performs provider registration
- `inner *Registry` -- the real registry, created inside the `once.Do` block

Expose all `Registry` methods (`ActiveProvider()`, `Active()`, `SetActive()`, `Register()`) but route through the lazy wrapper. `ActiveProvider()` calls `r.once.Do(r.initFn)` before delegating to `r.inner`.

New constructor:
```go
func NewLazyRegistry(initFn func() *Registry) *LazyRegistry
```
</action>

<acceptance_criteria>
- LazyRegistry compiles and passes `go vet ./internal/integrations/provider/...`
- Existing provider tests still pass
- `initFn` is called exactly once on first method invocation
</acceptance_criteria>

### Task 2: Refactor main.go startup to defer provider registration

<read_first>
- cmd/m31a/main.go:271-450
- internal/integrations/provider/registry.go
</read_first>

<action>
In `cmd/m31a/main.go`, replace the eager provider registration block (lines 421-449) with a `LazyRegistry` that captures the registration logic in a closure.

Move the keychain init (`keychain.New()`, `cfg.ResolveAPIKeys(kc)`) and provider registration into the lazy init function. The `LazyRegistry` is created early but the closure only executes when `ActiveProvider()` is first called.

Preserve the `hasProvider` check by calling `registry.Active()` which also triggers lazy init -- this is fine because `Active()` returns empty string if no provider, and the error path still works.

The config file load must remain eager (needed for `--model` flag resolution). Only keychain and provider registration are deferred.
</action>

<acceptance_criteria>
- `m31a --version` completes without triggering provider registration (verified by no keychain init log in debug mode)
- `m31a --prompt "hello"` triggers provider registration and works correctly
- TUI launch triggers provider registration on first LLM call
- `go vet ./cmd/m31a/...` passes
</acceptance_criteria>
