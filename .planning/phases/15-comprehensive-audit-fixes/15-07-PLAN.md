<objective>
Fix audit findings **H-8, H-10, H-13 (High) and M-25, M-26 (Medium)**
in the TUI segment rendering and concurrency surface.

- **H-8** — Stream segment type transition has a race. When the
  LLM sends `StreamChunkMsg{Type: "thinking"}` followed by
  `StreamChunkMsg{Type: "content"}`, the active segment type is
  read and written in `handleStreamMsg` without an explicit
  transition close. A `StreamDoneMsg` arriving during the
  transition can leave the segment in `thinking` state, and the
  final message renders an empty thinking block.

- **H-10** — `RenderHeader` runs on every `TickMsg` (1Hz) and
  re-formats the entire header string via `lipgloss`. When the
  state is unchanged, the output is identical but the cost is
  paid every second. On a 60Hz tick, this is 60 re-renders per
  second for the same string.

- **H-13** — Verify model's self-heal/skip keys (`H`/`S`) only
  work when more than one task is selected. A single-task
  selection falls into an `else` branch that does nothing.

- **M-25** — `StartStreamCmd` (in `internal/tui/streaming.go`)
  may have a defer-order bug. The channel close happens AFTER
  the cancel context call, so a final chunk can be lost on
  shutdown. (Note: 15-02 already touched this; verify the fix
  is in place and add a regression test if not.)

- **M-26** — Header cache invalidation does not consider
  `M31A_LOG_LEVEL=debug` mode. Debug mode adds extra fields to
  the header; the cache must be invalidated when the level
  changes at runtime.

**Output:** Atomic segment transitions, cached header with
smart invalidation, verify key fix for single-task selection,
regression test for stream shutdown ordering, debug-mode header
invalidation. One new test file with 4 race-detector tests.
</objective>

    **1. Segment transitions are explicit (H-8)**
    Refactor `handleStreamMsg` in `repl_stream.go` so that
    switching segment types is always paired with closing the
    prior segment:
    ```go
    case StreamChunkMsg:
        if msg.Chunk.Type != m.activeSegmentType {
            // close prior segment
            m.closeActiveSegment()
            m.activeSegmentType = msg.Chunk.Type
        }
        m.appendToActiveSegment(msg.Chunk)
    case StreamDoneMsg:
        m.closeActiveSegment()
        m.activeSegmentType = ""
    ```
    Where `closeActiveSegment` is a helper that:
    - Stamps the duration of the segment (if it was a thinking
      block, the duration_ms is now known)
    - Marks the segment as no longer being written
    - Does NOT clear `activeSegmentType` itself (the caller
      does, or the next chunk does)

    The function MUST be pure (no goroutines, no external
    state) — the BT Update() loop is single-threaded; the
    race comes from out-of-order message delivery, not from
    goroutines.

    **2. Stream shutdown ordering (M-25)**
    In `StartStreamCmd`'s cleanup goroutine, ensure the order:
    1. Cancel the request context
    2. Drain the stream channel (read until closed or empty)
    3. Close the channel
    Use `defer` carefully — `defer close(ch)` runs LAST, so
    the cancel and drain must complete BEFORE the defer fires.
    Pattern:
    ```go
    go func() {
        cancel()
        for range streamCh { /* drain */ }
    }()
    ```
    Wrap in a `sync.Once` so cleanup is idempotent.

    **1. Header cache on AppState (H-10)**
    Add to `AppState` (in `internal/tui/app.go`):
    ```go
    headerCache        string
    headerCacheKey     uint64  // hash of (model, provider, context_used, context_total, status, log_level, last_update_ts)
    headerCacheValid   bool
    ```
    The cache key is a `uint64` hash (use `fnv.New64a()` from
    `hash/fnv`) over a tuple of the input values. When any
    input changes, the hash differs and the cache is
    invalidated.

    In `RenderHeader`:
    ```go
    func RenderHeader(m *AppState) string {
        key := computeHeaderKey(m)
        if m.headerCacheValid && m.headerCacheKey == key {
            return m.headerCache
        }
        s := renderHeaderUncached(m)
        m.headerCache = s
        m.headerCacheKey = key
        m.headerCacheValid = true
        return s
    }
    ```

    **2. Invalidate on TickMsg (H-10)**
    The TickMsg handler in `AppState.Update()` sets
    `m.headerCacheValid = false` (the key recomputation will
    produce a new hash if the timestamp changed; this is the
    cheap invalidation path). The actual render only happens
    if the recomputed key differs.

    **3. Debug-mode invalidation (M-26)**
    The `computeHeaderKey` includes
    `os.Getenv("M31A_LOG_LEVEL")`. If the env var changes at
    runtime (rare but possible in test setups), the key
    changes and the header re-renders with the new fields.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Stream goroutine → BT Update loop | The stream goroutine never writes to AppState directly. It sends `tea.Cmd` returning `tea.Msg`. The single-threaded Update loop is the sole writer. |
| TickMsg → RenderHeader | TickMsg fires at 1Hz; the render path must be cache-friendly to avoid wasting CPU. |
| Verify key handler → task list | Key events must not panic on out-of-range selections. The selection index is untrusted input from the user. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation |
|-----------|----------|-----------|-------------|------------|
| T-15-07-01 | Tampering | Stream segment stuck in "thinking" | mitigate | H-8: explicit closeActiveSegment on type change and on Done |
| T-15-07-02 | Denial of Service | Header re-render every TickMsg | mitigate | H-10: cache with key-based invalidation |
| T-15-07-03 | Denial of Service | Stream shutdown loses final chunks | mitigate | M-25: cancel → drain → close ordering |
| T-15-07-04 | Information Disclosure | Log level change not reflected in header | mitigate | M-26: include log level in cache key |
| T-15-07-05 | Elevation of Privilege | Verify model panics on out-of-range selection | mitigate | H-13: bounds check before heal/skip |
