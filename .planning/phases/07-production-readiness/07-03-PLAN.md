Create `SUPPORT.md` per D-05 (rolling support policy). The document must contain five sections:

**1. Versioning Policy:** Semantic versioning (MAJOR.MINOR.PATCH). MAJOR bump required for: breaking changes to pkg/extensions types (interface changes, method removal), config schema changes (TOML key removal/rename), CLI flag removal/rename. MINOR bump for: new features with backward compatibility, new extension points, new config options. PATCH bump for: bug fixes, security fixes, documentation fixes. Reference conventional commits (feat:, fix:, etc.) that drive version bumps.

**2. Support Windows per D-05:**
- Current release: full support (bug fixes, security fixes, new features, documentation)
- Previous minor release: security fixes only for 6 months from current release date
- Major versions: security fixes only for 12 months from major release date
- Version support table showing: version, release date, EOL date, support level

**3. EOL Policy:** EOL dates published in GitHub Releases and SUPPORT.md. 6-month deprecation notice before removing features. After EOL, no patches (security or otherwise). Users should upgrade to supported versions.

**4. Deprecation Process:** Deprecated features emit log warnings via slog.Warn when used. Deprecation documented in CHANGELOG with removal timeline (minimum 6 months). Config fields marked deprecated in config types with deprecation comment. CLI flags produce warning when used. Removal happens in next MAJOR version after deprecation period.

**5. Security Reporting:** Private disclosure via GitHub Security Advisories (not public issues). Response timeline: acknowledge within 48 hours, assess severity within 1 week, provide fix or mitigation within 2 weeks for critical/high, within 1 month for medium/low. Credit reporters in release notes (unless they prefer anonymity).

Write the document in clear, professional markdown. Use tables for support windows and versioning rules. Include a "Last Updated" date at the top.
